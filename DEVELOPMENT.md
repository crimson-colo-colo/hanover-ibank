# Development Documentation

## Overview

Stack is outlined in [Google Docs](https://docs.google.com/document/d/1iVIqe-Ds2lOzQZnCSjM4QencB0RMr8g5wRizokCNwEE/edit?tab=t.pqez699negup#heading=h.mhe5j9jcjb69).

Our package manager is [**Bun**](https://bun.sh/), which is used for running
scripts, managing dependencies, and more. Use `bun i` to install dependencies
and `bun <script>` to run scripts defined in `package.json` or in the `cli`
directory. Avoid using npm, yarn, or pnpm to run scripts or manage dependencies,
as this can cause dependency duplication and other issues.

File structure:

- [**.idea**](./.idea), [**.vscode**](./.vscode) - IDE configuration files, e.g. for recommended extensions and settings
- [**cli**](./cli) - sysadmin CLI for interacting with the application
    - [**cli/commands**](./cli/commands) - each command gets its own file exporting a `Command` class
- [**prisma**](./prisma) - database stuff
    - [**prisma/migrations**](./prisma/migrations) - generated SQL migration files, generated by `bun db:migrate dev`
    - [**prisma/seed-data**](./prisma/seed-data) - sample data for seeding the database in development, used by `bun db:seed`
    - [**prisma/schema.prisma**](./prisma/schema.prisma) - Prisma schema
    - [**prisma/seed.ts**](./prisma/seed.ts) - script for seeding the database with sample data in development, run with `bun db:seed`
- [**public**](./public) - Vite public directory, static assets go here
- [**server**](./server) - Node.js-compatible Express server
    - [**server/generated**](./server/generated) - generated TypeScript types from Prisma schema, generated by `bun db:generate`
    - [**server/routers**](./server/routers) - tRPC subrouters, each feature gets its own file
    - [**server/database.ts**](./server/database.ts) - Prisma singleton instance and database connection logic
    - [**server/env.ts**](./server/env.ts) - environment variable parsing and validation with Zod (import this instead of accessing `process.env` directly)
    - [**server/logger.ts**](./server/logger.ts) - logger instance using Pino
    - [**server/main.dev.ts**](./server/main.dev.ts) - entry point for the server in development, with Vite in middleware mode for HMR
    - [**server/main.ts**](./server/main.ts) - entry point for the server in production, without Vite
    - [**server/router.ts**](./server/router.ts) - tRPC app router - add subrouters to `appRouter` here
    - [**server/trpc.ts**](./server/trpc.ts) - tRPC-related stuff like context and utilities for creating routers and procedures
- [**src**](./src) - React client application
    - [**src/assets**](./src/assets) - static assets like images (not served automatically - must be imported and used in components)
    - [**src/components**](./src/components) - shared React components
    - [**src/dev**](./src/dev) - React Buddy configuration
    - [**src/lib**](./src/lib) - client-side libraries and business logic (i.e. anything that isn’t a React component or page route)
    - [**src/routes**](./src/routes) - React components for each page route - files in here will be automatically edited by TanStack Router
    - [**src/env.ts**](./src/env.ts) - environment variable parsing and validation for the client, similar to `server/env.ts` but for client variables (e.g. `VITE_` variables. Import this instead of accessing `import.meta.env` directly)
    - [**src/main.tsx**](./src/main.tsx) - entry point for the React application (editing not recommended)
    - [**src/router.tsx**](./src/router.tsx) - TanStack Router configuration (editing not recommended)
    - [**src/routeTree.gen.ts**](./src/routeTree.gen.ts) - automatically generated route tree for TanStack Router (do not edit)
    - [**src/styles.css**](./src/styles.css) - global CSS styles (prefer Tailwind for styling, but can add global styles here if needed)

## Commands

**Everyone:**

- ⭐ **`bun db:start`** - start local database and object storage
- ⭐ **`bun dev`** - start application (start database first)
- ⭐ **`bun db:stop`** - stop database
- ⭐ **`bun db:generate`** - generate Prisma TypeScript client with new schema
  changes (run after changing the schema)
- **`bun db:seed`** - ⚠️ reset database and object storage and insert sample
  data. Don’t run if you have any data in the DB you want to save\!
- **`bun db:migrate dev`** - create a new migration from schema changes and
  apply it. Also applies to any pending migrations (e.g. created by others but
  not applied by you yet).

**Backend-specific:**

- **`bun db:migrate dev --create-only`** - create a new migration but doesn’t
  apply it. Useful for SQL only changes (e.g. adding constraints that can’t be
  represented in the Prisma schema) or reviewing the generated SQL before
  applying. Run `bun db:migrate dev` after reviewing/editing to apply.
- **`bun db:migrate reset`** - ⚠️ reset database migrations to match disk.
  Useful if you apply a migration but delete it afterwards because it was
  broken. Causes data loss!

## Environment Variables

`.env.development` contains the environment variables for development. So far
there are no secrets that need to be kept out of source control, so this file is
checked in. Do NOT add any secrets to this file!

- `NODE_ENV` - set to `development` for development and `production` for
  production. Affects logging and error messages.
- `PORT` - port to run the application on.
- `APP_URL` - base URL of the application. Used for generating links in emails
  and other places.
- `APP_SECRET` - unused for now, but will be used for signing cookies and other
  secrets in the future. Should be a long, random string in production.
- `DATABASE_URL` - connection string for the PostgreSQL database. The default is
  configured for the local development database started with `bun db:start`.
- `S3_ENDPOINT`, `S3_PORT`, `S3_SSL`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`,
  `S3_BUCKET` - configuration for the S3-compatible object storage. The defaults
  are configured for the local MinIO instance started with `bun db:start`.

## I want to...

### Run the application in development

- Ensure Docker is installed and running on your machine (`docker info` to check).
- Run `bun db:start` to start the local PostgreSQL database and MinIO object storage instances in Docker containers. Keep this running while you work on the
  application.
- Run `bun dev` to start the development server with Vite and the Express server in middleware mode for HMR. The application should be available at `http://localhost:3000`.
- Make changes to the code - the server will automatically restart when you make
  changes to server files, and the client will automatically reload when you
  make changes to client files.
- To stop the development server, press `Ctrl+C` in the terminal. To stop the
  database, run `bun db:stop`.

### Add a new page

- Start the database (`bun db:start`) and run the dev server (`bun dev`).
- Create a new file in `src/routes`, using the directory structure to describe
  the page path (e.g. `https://website.com/settings/profile` would be at
  `src/routes/settings/profile.tsx`). TanStack will automatically fill out the
  routing boilerplate for you; edit the generated React component to add content
  to the page.
- To allow users to navigate to the page, considering editing
  [**Navigation.tsx**](./src/components/Navigation.tsx) to add a link to the new
  page.
- To add path parameters, use \$paramName as a route segment (e.g.
  `src/routes/users/$userId.tsx` for `https://website.com/users/123`). To access
  the parameter in the component, write `const { userId } = Route.useParams()`
  or access `params.userId` from the route loader.

Read more about
[TanStack Router](https://tanstack.com/router/latest/docs/overview) and
[path params](https://tanstack.com/router/latest/docs/guide/path-params) in the
documentation.

### Add a new server-side procedure for the client to call

- Create or edit a file in `server/routers` to add a new tRPC router or
  procedure (follow the existing code as an example).
- Export the router and add it to `appRouter` in
  [**server/router.ts**](./server/router.ts). To call the procedure from the
  client, import `trpc` or `trpcClient` from
  [**src/lib/trpc.ts**](./src/lib/trpc.ts); you can either call procedures on
  `trpcClient` directly in a side effect (e.g. in a `useEffect`), or call
  procedures on `trpc` inside `useQuery` or `useMutation` for automatic caching
  and state management.
- Also consider using TanStack Router's data loading APIs for page-level data
  fetching for improved UX.

Read more about [tRPC](https://trpc.io/docs) or
[data loading in TanStack Router](https://tanstack.com/router/latest/docs/guide/data-loading)
for more information.

### Add a new sysadmin CLI command

- Create a new file in `cli/commands` that exports a `Command` class (follow the
  existing code as an example). The `paths` property on the class defines the command name that you will run in the terminal (e.g. `bun cli users create` for `paths = [["users", "create"]]`).
- To define arguments, define instance properties in your class that are set to
  `Option.String()`, `Option.Boolean()`, etc. from the `clipanion` library.
- Define the `async execute()` method on the class, which will be called when
  the command is run. This is where you put the logic for your command.
- Register the command in [**cli/cli.ts**](./cli/cli.ts) by importing the
  command and calling `cli.registerCommand()`.
- Start the dev server if it isn't running (`bun dev`) and run the command in a
  separate terminal with `bun cli <path> [args]`.

Read more in the [documentation](https://mael.dev/clipanion/docs).

### Add a new database table or change the schema

- Edit the Prisma schema in [**prisma/schema.prisma**](./prisma/schema.prisma)
  to add a new model or edit an existing one. (If your schema change can't be
  expressed in Prisma, (e.g. custom check constraints, skip this step and
  continue on.)
- Start the database (`bun db:start`) and run `bun db:migrate dev --create-only` to generate a new
  migration file. Enter a name for what you changed/plan to change when
  prompted. This will create a new SQL migration file in `prisma/migrations`.
- Edit/review this file to make sure the SQL looks correct or add any additional
  SQL if needed. Remember to wrap table names in double quotes and ensure they
  match exactly with the model names in the Prisma schema. If you aren't
  confident in your SQL, ask a teammate to review it before applying.
- Once you’re satisfied with the migration, run `bun db:migrate dev` to apply
  it. If you need to reset the database to match the migrations on disk (e.g. if
  you applied a migration but then deleted it), run `bun db:migrate reset` (⚠️
  causes data loss).
- Regenerate the Prisma client with `bun db:generate` to update the generated
  TypeScript types based on the new schema. Commit all of these changes
  together.

### Seed the database with sample data

- Start the database (`bun db:start`) and run `bun db:seed`. This will reset the
  database and object storage, so don’t run it if you have any data you want to
  keep.
- To add new sample data, edit the seed script in
  [**prisma/seed.ts**](./prisma/seed.ts) and add any static files (e.g. images)
  to `prisma/seed-data`. The seed script uses the Prisma client to insert data
  into the database, and the AWS SDK to upload files to object storage - read
  the code for examples of how to use these libraries.

## Conventions and Best Practices

- Format and lint your code before committing - run `bun format` and `bun lint`
  and fix any issues. Use Biome to format and lint, not the default WebStorm
  formatter/linter. You can set up WebStorm to run Biome on file save for a
  better developer experience.
- Follow existing code style and patterns as much as possible, especially for
  things like error handling, tRPC procedures, and database access. If you think
  something should be done differently, discuss it with the team and update the
  relevant code and documentation to reflect the new pattern.
- Write clear, specific, but concise commit messages that explain the "what" and
  "why" of the changes. Avoid vague messages like "fix bugs" or "update code".
  Follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)
  style for commit messages, using prefixes like `feat:`, `fix:`, `docs:`, etc.
  to indicate the type of change.
- Do NOT commit code changes to `main` - all changes must go through a PR
  reviewed by at least one other person. Follow [Conventional
  Branch](https://conventional-branch.github.io/) naming conventions for branch
  names, using prefixes like `feat/`, `fix/`, `docs/`, etc. to indicate the type
  of change. When your branch is ready, open a PR and request a review from at
  least one teammate.
- Your PR must pass CI checks and be approved by at least one other person
  before it can be merged. If your PR fails CI checks, fix the issues and push
  new commits until it passes.
- Perferrably, open an draft PR as early as possible to get feedback on your
  approach, even before the code is complete. This can help catch issues and
  improve the design before you invest a lot of time in implementation. Once the
  code is ready for review, mark the PR as ready and request reviews from
  teammates (you can always request one from Caleb!).
